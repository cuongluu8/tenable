# Media assets (club badges, country flags): local-first workflow

How to source, review, and publish entity images (`entities.image_key` →
an object in the `tenable-media` R2 bucket). Read this before running any
of `data/research/cache_media_locally.sh`, `upload_media.sh`, or
`apply_media_updates.sh`.

## The workflow

Four phases, each a separate script/step, so a mistake in one doesn't
force redoing the others and each step has something concrete to assert
before you move to the next:

1. **Research** (e.g. `scripts/find_club_badges.py`) resolves each missing
   entity to a real Wikipedia article + image filename via the MediaWiki
   API — no image bytes downloaded yet, just a manifest of
   `entity_id,entity_type,image_url` pointing at Wikipedia's
   `Special:FilePath` redirect for that filename.
2. **Cache locally** (`data/research/cache_media_locally.sh`) downloads
   every URL in that manifest to disk once, under
   `data/research/media_cache/<type>s/<entity_id>.<ext>`, and writes a new
   manifest (`manifest_local.csv`) pointing at those local `file://` paths.
3. **Review**, against the local cache — a generated review page (see the
   `club_badges_missing_review_v2.html` pattern) should point its `<img>`
   tags at the local cache directory (serve it with
   `python3 -m http.server` from `data/research/media_cache/`, or embed
   `file://` paths directly), **not** at Wikipedia. Approve/reject there.
4. **Upload to R2** (`data/research/upload_media.sh`), run against the
   *approved* local-file manifest — uploads straight from disk to R2. No
   network fetch from Wikipedia happens at this stage, and **nothing
   touches D1 yet**. Spot-check a few uploaded keys (`npx wrangler r2
   object get tenable-media/clubs/<id>.<ext>`, or just load a badge URL)
   before moving on.
5. **Apply to D1** (`data/research/apply_media_updates.sh`, given the
   `media_updates_<timestamp>.sql` file step 4 wrote out) — the actual
   `UPDATE entities SET image_key = ...` writes, local then production.
   Kept as its own explicit step on purpose: it's the one part of this
   whole pipeline that's genuinely hard to reverse, so it shouldn't just
   happen automatically at the end of a long unattended run.

`upload_media.sh` needs no code changes to support step 4 running against
local files: it downloads via `curl`, and curl reads `file://` URLs
exactly like `https://` ones (the only difference is `content_type` comes
back empty for local files, which the script already falls back from to
the file extension).

## Why this replaced the old single-phase approach (2026-09-07 incident)

The original approach hotlinked Wikipedia twice for the same image: once
in the review page's `<img src>` (444 images loading at once), and again
when `upload_media.sh` re-downloaded each approved URL fresh at upload
time. Sourcing 430 badges this way took **three separate manual passes**
over several hours and produced a string of misdiagnoses along the way:

- The review page loading 444 hotlinked images at once tripped Wikimedia's
  rate limiter (HTTP 429, some images just failing to load) — fixed at the
  time with `loading="lazy"` + a client-side retry, but the real fix is
  **don't hotlink hundreds of images from one page at all**.
- The first full upload run (430 rows, 1s/row) got rate-limited again —
  382 of 430 rows failed with Wikimedia serving an HTML block page instead
  of the image (a real HTTP 200, not a curl error — `upload_media.sh`'s
  content-type + doctype-sniffing validation is what catches this and
  stops it from silently uploading an HTML error page as a "badge").
- Two more manual retry passes (longer delays) were needed to clear the
  backlog, and were themselves still hitting the same rate limit
  intermittently.
- A "let it self-heal" fix was added to `upload_media.sh` (per-row retry
  with backoff — 10s/30s/60s/120s/240s), plus a proper descriptive
  `User-Agent` (the script had none — Wikimedia is known to treat a bare
  `curl/x.y` UA worse than a real one) and explicit `--connect-timeout`/
  `--max-time`/`--ipv4` so a hung or IPv6-flaky request can't block the
  whole run silently. `-sS` (not just `-s`) was also required — plain `-s`
  hides curl's own error text, which is why every earlier failure showed
  as a content-free "download empty/failed" instead of the real reason.
- Even after all that, one manifest file still failed **every single
  row** — not rate-limiting at all: it had been generated by Python's
  `csv.writer` (which defaults to `\r\n` line endings) and bash's
  `read` doesn't strip the trailing `\r`, so it rode along attached to the
  URL and curl correctly rejected it as malformed
  (`curl: (3) URL rejected: Malformed input to a URL function`). Lesson:
  when generating a manifest with Python, either use
  `open(path, "w", newline="\n")` or post-process with `tr -d '\r'` — and
  when a "network" failure is 100% reproducible on every row rather than
  intermittent, suspect the file, not the network.

None of this would have been necessary with the local-first workflow: one
download per image, ever, and the review step (previously the single
biggest source of hotlinked-request volume) touches zero network calls.

## Practical notes

- **Idempotent at every phase.** Re-running `cache_media_locally.sh`
  just re-downloads to the same local path. Re-running `upload_media.sh`
  overwrites the same R2 key and re-applies the same (idempotent) SQL
  `UPDATE ... WHERE id = ...`. Safe to interrupt and resume at any phase —
  each script feeds a `..._failed_<timestamp>.csv` you can re-run standalone.
- **Never edit a manifest file while a script might still be reading it.**
  Both scripts open the manifest once at the start of a `while read` loop
  and read it sequentially; truncating/rewriting the same path out from
  under a still-running process (e.g. from a second terminal, or an
  agent "cleaning up" concurrently) can silently truncate what that
  process sees. If you need to know the true remaining set after a run
  you're unsure fully completed, don't trust manifest bookkeeping —
  query D1 directly for which of your target `entity_id`s already have
  `image_key IS NOT NULL` and regenerate the manifest from that.
- **`upload_media.sh` never touches D1** — only `apply_media_updates.sh`
  does, and it always writes to both local and production (`--local` then
  `--remote`; no flag to do only one). If D1 is off-limits (quota,
  maintenance), that's the only script you need to hold off on — R2
  uploads can proceed freely and the resulting SQL file just waits until
  you're ready.
- Default per-row delay is 2s in both scripts; bump the trailing
  `sleep_seconds` argument if you still see frequent `RETRY` lines.
